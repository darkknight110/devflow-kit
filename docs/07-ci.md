# 接入 CI：让门禁成为结构强制

> **为什么必须有这一步**：`doctor`、`gate run`、提交信息钩子都靠**有人记得执行**。
> 没有 CI，门禁就只是"本地约定"——换台机器、重新 clone，什么都不剩，
> 也没有任何东西能拦住一个**跳过门禁的合并**。本文档把门禁接到流水线上。

---

## 一、一条命令生成配置

```bash
devflow ci --platform gitlab --item <变更>     # 生成 .gitlab-ci.yml
devflow ci --platform github --item <变更>     # 生成 .github/workflows/devflow.yml
devflow ci --platform gitlab --dry-run        # 只看会写什么，不落盘
```

生成后**必须改一处**：`DEVFLOW` 的获取方式（devflow 不随仓库分发）。
默认写好的是 `./devflow-kit/bin/devflow`，请按团队实际方式改（子模块 / 包管理器 / 镜像内预装）。

---

## 二、分工（刻意区分，否则 CI 会长期红灯）

| 检查 | 回答什么 | CI 中的位置 | 失败是否阻断 |
|---|---|---|---|
| `gate run` | **本次变更**是否达到门禁要求 | 必过 job | ✅ **阻断** |
| `doctor` | **门禁本身**是否可信（配置债务） | 报告 job | ❌ 默认不阻断 |
| `contract-scan --fail-on-drift` | 跨仓契约是否漂移 | 报告 job | ❌ 默认不阻断 |

**为什么这样分**：`doctor` 反映的是**配置问题**（一次性的、存量仓常有债务）。
若把它放进必过步骤，一个存量仓的配置债务会让**每一次推送都红灯** ——
**红灯一旦常态化，门禁就失效了**（这比没有门禁更糟）。

需要"配置零债务"时，用 `devflow ci --strict-doctor` 生成（`allow_failure: false`）。

---

## 三、生成的配置长什么样（GitLab）

```yaml
stages: [gates, report]

# 必过：本次变更是否达到门禁要求
devflow-gate:
  stage: gates
  script:
    - export DEVFLOW="${DEVFLOW:-./devflow-kit/bin/devflow}"
    - $DEVFLOW gate run <变更>

# 报告性质：门禁自身是否可信（配置债务，默认不阻断）
devflow-doctor:
  stage: report
  script:
    - $DEVFLOW doctor
  allow_failure: true
```

> **警告**：不要用 `|| true` 掩盖 `devflow-gate` 的失败 —— 那会让门禁**静默失效**，
> 属于本产品反复强调的"假通过"。要放过就在配置里显式写 `allow_failure`，让代价可见。

## 四、git 钩子与 CI 的关系（两者都要，但作用不同）

| 手段 | 生效时机 | 覆盖范围 | 是否随仓库分发 |
|---|---|---|---|
| **git 钩子**（`setup-hooks`） | 本地提交时 | 提交信息规范 | ❌ **不在版本控制里** |
| **CI**（`ci`） | 推送/合并请求时 | 全部门禁 | ✅ 随仓库走 |

```bash
devflow setup-hooks          # 安装提交信息钩子（每台新机器都要跑一次）
devflow setup-hooks --force  # 覆盖已有钩子（默认不覆盖，避免破坏别人的规范）
```

**关键事实：`.git/hooks/` 不在版本控制里。** 换机器、重新 clone 之后钩子**全部消失**，
而且不会有人提醒你 —— 所以钩子只是"顺手拦一下"，**真正的强制必须靠 CI**。

## 五、接入清单

- [ ] `devflow ci --platform <gitlab|github> --item <首发变更>`
- [ ] 改 `DEVFLOW` 的获取方式（让 CI 能拿到 kit）
- [ ] 确认 `devflow-gate` 在必过阶段、且**没有**被 `|| true` 掩盖
- [ ] 确认 `devflow-doctor` 与契约扫描是报告性质（`allow_failure` / `continue-on-error`）
- [ ] 每个开发者执行一次 `devflow setup-hooks`
- [ ] 本地先跑一遍生成的脚本，确认能通（`$DEVFLOW doctor && $DEVFLOW gate run <变更>`）

## 人工确认点在 CI 里的位置

生成的配置会在**报告 job** 里跑：

```bash
devflow review --all     # 列出每个变更的确认点进度：已签谁、待签什么
```

**它刻意不阻断**。理由：

| 若阻断 | 后果 |
|---|---|
| "人还没签字" 让每次推送红灯 | 团队会去关掉这个检查 ⇒ **比没有检查更糟** |

**真正的强制在门禁层**：`devflow gate run` 会校验签核记录（真实姓名 + 时间 + 结论，
且占位值不算），**没有签核就不许推进状态**。CI 这一层只负责**让待签项可见**。

要某人尽快签核时，把 CI 日志里这几行发给他即可（含变更、确认点、已签人）。
