# 工作流正典（Kit 视角）

**版本**：1.0.0　**适用**：devflow-kit 本体
**关系**：本文是**可执行正典**（引擎真正读取 `spec/*.json`）。设计背景与取舍见工作区内的《通用研发工作流设计方案 V3.0》。

---

## 一、一句话

**事实在文件里，动作在命令行与会话里，界面只是文件的投影。**
强制力来自**产物契约 + 状态机 + 可执行门禁**，不来自规范文本。

---

## 二、十条不变量（不可违反）

| # | 不变量 | 落地方式 |
|---|---|---|
| 1 | 技术栈无关 | 规范与引擎中不出现任何语言/框架名；命令由项目在 `devflow.json` 声明 |
| 2 | 契约先于实现 | 跨边界变更必须先冻结 `CONTRACT.md`，再并行实现 |
| 3 | 判据先于代码 | `SPEC.md` 的每条 AC 必须有判据与判据类型，否则 G1b 阻断 |
| 4 | 证据机器可核 | 每条门禁结果含命令原文、退出码、输出尾部；缺失由 G2 阻断 |
| 5 | 验证者隔离 | 验证记录由独立上下文产出；单人场景必须新开会话 |
| 6 | 门禁可执行且非恒真 | 无脚本的规则不算规则；恒真门禁由 G3 判为不可信 |
| 7 | 优雅降级 | 四档分级 + 六种 profile；**但判据不可裁剪** |
| 8 | 数据与呈现解耦 | 状态只存于 `.devflow/`；看板、终端输出皆为其视图 |
| 9 | 上下文预算即门禁 | G4 检查变更产物体积与指令链体积 |
| 10 | **验收必须经独立视角** | 自评不算验收：交付物必须让**未参与实现的人**只读文档跑一遍；该要求由 `examples/verify-independent.sh` 可执行化 |
| 11 | **提交信息只做概括** | 提交信息用于快速定位改动，不是变更日志或复盘文档：`<type>(<scope>): <摘要>` ≤72 字，正文 ≤3 条要点、无空行分段、总行数 ≤8；由 `tools/validate-commit-msg.mjs` 可执行校验（可装为 `commit-msg` 钩子） |

## 三、四档分级

| 档 | id | 适用 | 是否要 SPEC | 确认点 | 可跳过状态 |
|---|---|---|---|---|---|
| 微 | `micro` | 文案、样式、单文件 | 否 | 0 | 全部（只有状态记录） |
| 轻 | `light` | 单端 UI、纯前端页面、无接口变化的内部重构 | 是（极简） | 1 | 契约 |
| 标 | `standard` | 单仓功能开发、内部接口变化 | 是 | 2 | 无 |
| 重 | `heavy` | 跨仓、改对外接口、动数据与鉴权 | 是 | 3 | 无 |

**三条硬降档禁令**（引擎用 G7 做**启发式**比对，并**明示会漏报**）：

1. 碰接口字段 / 数据结构 / 鉴权 / 租户上下文 ⇒ 最低 `standard`；
2. 跨两仓及以上 ⇒ 必须 `heavy`；
3. 有测试基座的项目不得用 `micro` 逃避验证。

**升档允许且鼓励**：实现中发现影响面变大，立即停下升档并回报。**降档必须留痕**（写在 SPEC 身份表）。

## 四、七阶段与状态

```
draft → spec_ready → contracted → implementing → tested → verified → released
                         ↑              │           │          │
                         └──────────────┴───────────┴──────────┘
                                  任一门禁失败即回退
```

| 状态 | 必备产物（累积） | 进入条件 |
|---|---|---|
| `draft` | STATE / STATUS.json | 变更登记且档位留痕 |
| `spec_ready` | + GOAL.md（标准/重档）+ SPEC.md | 每条 AC 有判据与判据类型；标准档与重档还须有业务目标锚 |
| `contracted` | + CONTRACT.md | owner 唯一、破坏性判定、兼容策略 |
| `implementing` | + TASKS.md | 每任务有目标仓、写入范围、验收命令、对应 AC |
| `tested` | + coding_report.md | 项目门禁通过（或合法豁免）+ 负向对照可信 |
| `verified` | + verification.md + APPROVALS.md | 三态结论 + 确认记录 |
| `released` | + release/report.md | 报告卡含原始输出与观察窗口 |

**产物累积规则**：某状态的必备产物 = 沿状态链（`draft → … → 本状态`）累积的产物 ∩ 当前档位要求的产物。
档位声明了某产物（如 `release/report.md` 对轻档）**不等于**提前索要 —— 只有走到对应状态才要求。

**轻档与微档**允许 `spec_ready → implementing` 直连（跳过契约）。

## 五、门禁体系

### 5.1 判定符号（全系统统一）

| 判定 | 符号 | 含义 | 是否阻断 |
|---|---|---|---|
| pass | ✓ | 通过，**必须有证据** | 否 |
| unverified | ⚠ | **未验证通过**（负向对照缺失或恒真、启发式提示） | 否，但不得显示为 ✓ |
| exempt | ■ | 基线豁免（显示为警告） | 否 |
| blocked | ⛔ | 阻断 | **是** |
| fail | ✗ | 失败 | **是** |
| pending | ○ | 未运行 | 否 |
| stale | ⏸ | 确认点超时 | 否 |

### 5.2 九项门禁

| 门禁 | 名称 | 层级 | 检查什么 |
|---|---|---|---|
| G0 | 项目配置有效 | 阻断 | `devflow.json` 存在、合法、含 devflow 块、kit 版本满足、至少一个门禁 |
| G1 | 产物齐备 | 阻断 | 状态链所需产物存在 + 必填章节 + 必填列 + 最少行数 |
| G1b | 内容合规 | 阻断 | AC 有判据与类型；任务可追溯；验证覆盖全部 AC；确认记录达档位要求 |
| G2 | 证据形态 | 阻断 | 每条记录含命令、退出码、输出尾部 |
| G3 | 负向对照 | **标签** | 声明的必定失败命令必须返回非零；否则该门禁记 ⚠ |
| G4 / G4b | 上下文预算 | 阻断 | 变更产物体积超阻断线即阻断；指令链超限提示 |
| G5 | 状态一致 | 阻断 | STATE 与 STATUS.json 一致；**未知状态直接报错** |
| G6 | 基线豁免合规 | 阻断 | 豁免须登记原因与清除条件；大变更不得引用；新建项目禁止 |
| G7 | 变更面与档位匹配 | **标签** | 轻/微档却触碰契约或接口面 ⇒ ⚠ 需人工确认（启发式，会漏报） |
| G8 | 产物运行时健全性 | 阻断 | 构建退出码 0 但产物跑不起来（如小程序产物残留 `process.env`） |
| G9 | 发布前置门禁 | 阻断 | `release.requires` 声明的门禁在 released 前必须各有一条 pass 记录（⚠ 不算） |

### 5.3 doctor：门禁的可信度体检（只读）

门禁写得不对会**静默骗人**。doctor 专门回答一个问题：**现在这套门禁，能不能信？**

| 发现 | 严重度 | 触发条件 |
|---|---|---|
| D1 未声明任何门禁 | 阻断 | `gates` 为空 |
| D2 负向对照缺失 / 返回 0 / 脚本不存在 | 削弱 / 阻断 | 缺失⇒削弱；返回 0 或 127⇒阻断 |
| D3 测试门禁名存实亡（退出码 0 但没有测试在跑） | 阻断 | 输出出现 `Tests run: 0` 等 |
| D3 计数正则抓不到 / 未设测试数下限 | 削弱 | 正则无匹配 / 无 `require_min_tests` |
| D4 引用脚本不存在 / 不可执行 / 仍是占位脚本 | 阻断 | 缺文件、无执行位、含哨兵 `devflow:placeholder` |
| D5 命令以管道收尾（退出码可能被吞） | 削弱 | `run` 形如 `... | tail` |
| D6 项目根仅凭 `devflow.json` 判定 | 削弱 | 缺 `.devflow/` 目录 |
| D7 变更目录下有非目录文件 | 削弱 | — |
| D8 指令链体积超限 | 削弱 | 合计 > 64k 字符 |
| D9 未声明 kit 版本约束 | 提示 | `devflow.kit` 缺失 |

**每条发现必须同时给出「问题 + 依据 + 修法」**，缺一不可。结论只有三种：可以开工 / 强度被削弱 / 门禁不可信。

**占位脚本的哨兵机制**：`init` 生成的示例脚本带 `devflow:placeholder` 哨兵且**刻意返回非零**。
理由：「假装检查了」比「明确未配置」危险得多。识别用哨兵而不是文案 —— 文案一改检测就会静默失效（踩过）。

### 5.4 负向对照为什么是"标签"而不是"阻断"

要求每个门禁都提供"必定失败的命令"，在存量项目上是真实负担，结果是大家复制粘贴一个假脚本应付 —— **检查还在，意义没了**。
因此：**有对照且返回非零 ⇒ ✓；未声明或返回零 ⇒ ⚠（未验证通过）**，不阻断、也绝不给 ✓。

### 5.5 存量基线豁免

```jsonc
"test": {
  "run": "./scripts/test.sh",
  "require_min_tests": 1,
  "baseline_exempt": {
    "reason": "本仓历史无测试基座",
    "clear_when": "test_count > 0",
    "allowed_scope": ["ui-tweak", "copy-change"]
  }
}
```
三条缺一不可：**显式登记**、**显示为豁免而非通过**、**只减不增**（新建仓库禁止豁免，触碰接口/数据/鉴权不得豁免）。

---

### 5.6 为什么 `gate run` 的输出里看不到 G3

G3 是**标签级门禁**（不阻断），它的判定结果贴在**每一条项目门禁行**上，而不是单独占一行：

```
✓  test   exit=0 count=12  负向对照返回 1，门禁可信      ← 这句就是 G3 的结论
⚠  build  exit=0            未声明负向对照：结果标记为未验证通过   ← G3 判它不可信
```

所以 `gate run` 会显示 9 行（`G0 G1 G1b G2 G4 G4b G5 G6 G7`）而不是 10 行 —— **别以为 G3 没跑**；
判据是那行门禁的结论，不是有没有独立的徽章。

## 六、证据形态契约

每条门禁结果必含：`gate / project / command / exitCode / outputTail / startedAt / durationMs / verdict`。

**三条禁令**：不得用管道退出码判断结论；不得只写结论不写证据；不得把未验证写成已验证。

## 七、人工确认点

| 确认点 | 触发 | 记录位置 | 档位要求 |
|---|---|---|---|
| AP1 需求与判据 | SPEC 完成 | `APPROVALS.md` | light / standard / heavy |
| AP2 契约冻结 | 跨边界变更 | `APPROVALS.md` | standard / heavy |
| AP3 发布批准 | 发布前 | `APPROVALS.md` | light / standard / heavy |

**两条硬约束**：

1. 确认点**只能发生在编排者（主会话）** —— 子代理运行时无法向用户提问；
2. 确认结果**必须落成文件**，口头确认不作为证据。所以编排天然是**两段式**。

## 八、角色与切分

| 角色 | 上下文 | 写权限 | 禁止 |
|---|---|---|---|
| 编排者 | 主会话 | `.devflow/**`、`devflow.json`、规范与模板、**契约文件** | 不写业务代码；未确认不推进 |
| 实现者 × N | 独立子代理 | **仅自己任务声明的写入范围** | 不跨仓、不碰契约、不擅自重构 |
| 验证者 | 独立子代理（强制隔离） | 仅变更目录内报告 | **不得修改被验证物**、不得发起发布 |

**切分三原则**：一个子代理 = 一个写入范围；契约只有编排者可改；同仓并行必须独立工作树与分支。
**分组规则**：按任务声明的**写入范围文件集合是否相交**计算，不得凭感觉切分。

**契约质量的硬检验**：两个互不通信的实现者首次联调即对接成功 ⇒ 契约合格；对接失败 ⇒ 回退契约阶段，不许靠"双方沟通对齐"绕过。

## 十一、独立验证协议（本项目最贵的经验）

**结论：没有独立验证的验收，等于没验收。**

第 4 期做过一次对照：当时所有自检（19 条）与端到端断言（40 条）全绿，
但一个**只读文档、全新上下文**的验证者**在第 1 步就踩空** ——
文档示例写着 `--stack node`，而工具只认 `java-maven / node-jest / python-pytest / go-test`，
且当时无效值只警告、不报错、还照旧落盘。**40 条断言里没有一条覆盖"文档写错了"这种缺陷。**

### 协议（三条，缺一不可）

1. **谁验**：**未参与实现的人**，或**全新上下文的子代理**。实现者本人及其上下文**不得**充当验证者。
2. **验什么**：只给 `README` + `02-adoption-guide` + `03-daily-workflow`，
   在**陌生目录 + 不同于既有样例的技术栈**上，走完「接入 → 建变更 → 提测 → 验证 → 发布」。
   **禁止**阅读正典、`spec/*.json`、`scripts/*.mjs`、`examples/*`。
3. **怎么算通过**：只凭文档走通；**任何一处"只能靠猜"或"只能靠 `--help`"都算缺陷** ——
   要么修文档，要么修产品，并把修法钉成 selfcheck 或 `verify-independent.sh` 的断言。

### 可执行化

| 载体 | 作用 |
|---|---|
| `examples/verify-independent.sh` | 机器可跑的"陌生人路径"：断言文档卫生（无非法取值）、文档覆盖陌生人必问的六件事、只按文档走通一条变更 |
| `docs/02` / `docs/03` 的断言 | 文档卫生由脚本保证，不靠人工核对 |

**流程要求**：交付前跑**全部验收**（`bash examples/verify-all.sh`：自检 + 六套端到端，含独立视角、人的闭环与四档位）；**版本发布前**还必须有一次**人工独立复跑**。

## 十一之二、提交信息规范（可执行）

**为什么单列一章**：提交信息是团队最常读、也最容易写坏的产物。它一旦允许"讲故事"，
就会变成 20–40 行的复盘文档 —— 阅读成本高、与代码注释和报告重复、在 `git log` 里几乎无人看。
所以规则必须**简短且可机器校验**。

**格式**：

```
<type>(<scope>): <摘要>          # 标题 ≤72 字，不以句号结尾
                                 # 空一行
- 要点一（≤100 字）                # 正文最多 3 条
- 要点二
```

**type**：`feat | fix | test | refactor | perf | docs | chore | build | ci | revert`
**scope**：必填，如 `mp` / `contract` / `lint` / `app` / `coupon`

**硬规则**：

| 规则 | 说明 |
|---|---|
| 标题 ≤72 字 | 超长标题在 `--oneline` 里被截断，失去定位作用 |
| 正文 ≤3 条要点 | 只写"改了什么"，不写推导过程 |
| **不允许空行分段** | 空行分段是"讲故事"的入口，一律禁止 |
| 总行数 ≤8 | 超过说明该放进报告或 MR 描述 |
| 不写"验证：…" | 验证证据属于 `verification.md` / 门禁记录，不属于提交信息 |

**执行方式**：

```bash
# 校验单条信息
node tools/validate-commit-msg.mjs --text "fix(mp): 修正 base 前缀"

# 装为钩子（每仓一次）
cp tools/validate-commit-msg.mjs .git/hooks/commit-msg && chmod +x .git/hooks/commit-msg
```

**与其它产物的分工**（避免重复）：

| 内容 | 归处 |
|---|---|
| 一句话概括改了什么 | **提交信息** |
| 为什么这样改、推导过程、取舍 | `coding_report.md` |
| 实测证据、命令与退出码 | `verification.md` / `STATUS.json` |
| 契约与端点约定 | `CONTRACT.md` |

## 十二、已知局限（设计上无法消除，只能明示）

1. 单人场景下引擎**无法强制**确认点（没有第二个人）；
2. G7 是**启发式**，存在漏报；
3. 未提供负向对照时只能标 ⚠，门禁可能在无声地恒真 ⇒ 靠季度棘轮只减不增地消除；
4. 预算用**字符估算**而非精确 token；
5. 看板**只读**，不能在看板上操作状态（刻意设计，保住门禁的强制力）；
6. 静态 HTML **无法选择工作区**（靠命令行或 `DEVFLOW_ROOT`）；
7. 文档与规范存在**漂移风险** ⇒ 每条条款必须挂门禁或角色契约。
8. **自评偏差**（最贵的一条）：自己写的验收会系统性漏掉「外人第 1 步就踩空」的地方 —— 交付前必须跑 `examples/verify-independent.sh`，版本发布前由未参与实现的人复跑一遍。
9. **夹具偏差**：自造夹具会系统性漏掉"真实工程才有的形态"（多测试类、自带 wrapper、既有约定）—— 第 5 期一次真实试点就抓出 4 个前四期未覆盖的缺陷。**每期至少要有一次真实工程试点**（见 `docs/06-pilot-report.md`）。
