# AI 写的方案怎么验收？用门禁，不用感觉

> AI 最擅长的不是写对，而是**写得像对的**。
> 所以验收 AI 的产出，靠"读一遍觉得还行"是无效的——你需要的是**退出码**。

这篇讲三件事：什么能机械验证、怎么设计一条**不会骗人**的门禁、以及为什么"发布"要单独设一道闸。

---

## 一、先说结论：能验的只有四类

| 能机械验证 | 不能机械验证 |
|---|---|
| 产物**在不在**（文件、章节、表格列） | 方案**对不对**（业务判断） |
| 内容**填没填**（占位符、空章节） | 写得好不好（品味） |
| 证据**全不全**（命令、退出码、输出尾部） | 客户认不认（关系） |
| 门禁**是不是恒真**（负向对照） | 市场时机 |

**门禁只做左边这一列。** 右边那列交给人和时间——把能机械化的部分机械化，人才有空判断真正需要判断的事。

---

## 二、一条"不会骗人"的门禁长什么样

大多数团队的门禁长这样：

```json
{ "test": { "run": "npm test" } }
```

它只回答"命令退出码是不是 0"。这不够——因为**退出码为 0 有两种可能**：
真的通过了，或者**根本没检查**。

一条可信的门禁至少要能回答四个问题：

1. **跑的是什么**（命令原文）；
2. **退出码是多少**；
3. **输出尾部是什么**（出事时能定位）；
4. **它是不是恒真**（负向对照：拿一个必定失败的输入，它必须失败）。

第 4 条最容易被跳过，也最值钱。

### 真实翻车案例（都来自我们的自检）

| 写法 | 为什么骗人 | 正确做法 |
|---|---|---|
| `"run": "exit 0"` | 永远通过 | 声明负向对照，必须返回非零 |
| 负向对照返回 1，但实际是 `No test files found` | 断言从没执行 | 同时要求**失败证据**（`Failures: 1`、`AssertionError`） |
| `cmd \| tail -1` 取结论 | 管道退出码来自 `tail`，恒为 0 | 取被调用命令自身的退出码 |
| 计数正则只取第一行 | 多模块把 15 个测试记成 4 个 | 累加所有匹配 |
| 测试数下限设为 0 | 0 个测试也算"通过" | 给真实下限 |

这五条不是理论，是我们踩过并把每一条都做成自检用例的。

## 三、为什么还要"状态机"

门禁只回答"这一步能不能过"，不回答"现在该做什么"。

一个变更从想法到发布，中间有必然的顺序：需求 → 判据 → 契约 → 实现 → 提测 → 验证 → 发布。
没有状态机，就会出现：**代码写完才补需求、发布前才想起验证**。

状态机的价值不是流程感，是**缺件即拒绝**：

```
草稿 → 需求就绪 → (契约冻结) → 实现中 → 待验证 → 已验证 → 已发布
```

每一步都声明"进入这一步必须有哪些产物"。少一件，`advance` 直接拒绝，
并告诉你**缺哪个文件、缺哪一节**——而不是让你自己猜。

轻档可以跳过"契约冻结"；微档可以跳过大部分——**跳过是声明，不是漏跑**。

---

## 四、发布要单独设一道闸（G9）

有一种很常见的失真：**提测时门禁是绿的，发布时拿的还是那次的记录。**

代码早改过了，记录还是绿的。于是发布这个词，变成了"点一下"。

我们的做法是给发布加一条硬要求：项目声明 `release.requires`，
里面列出的门禁，在进入"已发布"之前必须**各有一条 pass 记录**；并且：

- 记录必须**比最近一次产物修改更新**（旧记录不算证据）；
- `⚠ 未验证通过`和"豁免"都不算通过——发布不接受"大概没问题"；
- `advance --to released` 会**先现跑一遍**门禁，不是等你手动跑。

想用 `--no-run` 跳过？可以，但旧记录会因"新鲜度"被判无效。

---

## 五、怎么开始（不重构你的项目）

1. 先给现有项目接上：`curl -fsSL …/install.sh | sh`，`devflow init`，`devflow doctor`；
2. **信 doctor，不信自己**：它会告诉你哪条门禁不可信、怎么修；
3. 把"测试/构建/数据体检"写成项目自己的命令，配上**负向对照**；
4. 给发布加 `release.requires`，让"能不能发"由退出码决定。

---

## 一句话

**AI 让"产出"变得便宜，于是"验收"变成了瓶颈。**
门禁不提高产出速度，它只保证一件事：**你说"完成"的时候，有东西能证明。**
