# 基础标准与自定义规则

> 本文档说明 **devflow 对任何项目都成立的最低要求**，以及**你如何制定或覆盖自己的规则**。
>
> 标准的事实来源是 [`spec/standards.json`](../spec/standards.json)（机器可读，单一来源）；
> 本文档是它面向人的说明。**两者不一致时以 `standards.json` 为准**，
> 并应把本文档视为缺陷（用 `devflow selfcheck` 与人工复核兜底）。
>
> 运行 `devflow standards` 可对**当前项目**逐条判定。

---

## 一、判定结果的三种含义（务必先读这一节）

| 标记 | 含义 | 你该做什么 |
|---|---|---|
| `✓ 满足` | 引擎已按判定方式确认达成 | 无需处理 |
| `⛔ / ⚠ 未满足` | 未达成且未登记豁免 | 按 `后果` 处理：`block` 必须修或登记豁免；`weaken` 可接受但要留痕 |
| `— 不适用` | 本条对当前项目/本次变更不成立（附原因） | 无需处理，但**要看清原因**："不适用"不等于"满足" |

> **"不适用"绝不等于"通过"。** 如果原因写的是"未取到门禁记录，无法判定"，那表示**结论未知** —— 先跑一次 `devflow gate run` 再来判。

## 二、基础标准清单

`档位` 列表示适用档位（`all` = 全部）。`判定` 列：`机器` = 引擎自动判定；`人工` = 需人确认并在文档留痕。

### 门禁强度

| id | 档位 | 判定 | 违反后果 | 可豁免 | 要求 |
|---|---|---|---|---|---|
| `STD-GATE-TEST-RUNS` | all | 机器 | 阻断 | 是 | 测试门禁必须真的跑到测试。`Tests run: 0`、`No tests to run`、`No test files found` 一律视为空转 |
| `STD-GATE-NEGATIVE-CONTROL` | light+ | 机器 | 削弱 | 是 | 每个声明的项目门禁都要有 `negative_control` |
| `STD-GATE-NEGATIVE-EVIDENCE` | all | 机器 | 削弱 | **否** | 负向对照退出码非 0 **且** 输出含失败证据（`FAIL`/`AssertionError`/失败计数/`BUILD FAILURE`）才算有效 |
| `STD-GATE-HONEST-EXIT` | all | 机器 | 削弱 | 是 | 门禁脚本必须以退出码表达真实结论；无条件 `exit 0` 的包装脚本须登记 `baseline_debt` |

**关于 `STD-GATE-HONEST-EXIT` 的分级（刻意设计）**：

- 门禁**谎报通过**（脚本内容层面）⇒ 由 `doctor` 的 D4 **阻断**；
- 门禁**诚实失败**但已登记 `baseline_debt` ⇒ 本条判"未满足/削弱"并显示清除条件，**不阻断**。

> 若"诚实登记债务"也被阻断，使用者会倾向**删掉声明** —— 那比谎报更糟。

### 测试与证据

| id | 档位 | 判定 | 违反后果 | 可豁免 | 要求 |
|---|---|---|---|---|---|
| `STD-TEST-BASELINE` | all | 机器 | 阻断 | 是 | 要么真实跑到 ≥1 个测试，要么登记 `baseline_exempt`（含 `reason` 与 `clear_when`） |
| `STD-EVIDENCE-BY-COMMAND` | light+ | 机器 | 阻断 | **否** | `verification.md` 的"证据"节必须含可复现的命令与结论；禁止只写"已验证" |
| `STD-EVIDENCE-INDEPENDENT-REVIEW` | standard+ | 机器 | 阻断 | **否** | 写了"独立复核"就必须有复核方标识/时间戳，或原样转录并标注转录者 |
| `STD-UNVERIFIED-EXPLICIT` | all | 机器 | 削弱 | **否** | 因环境受限等无法验证的门禁必须判为"未验证"并写明原因；不得显示为通过、也不得阻断 |

### 契约（跨边界变更）

| id | 档位 | 判定 | 违反后果 | 可豁免 | 要求 |
|---|---|---|---|---|---|
| `STD-CONTRACT-FROZEN` | heavy | 机器 | 阻断 | **否** | 变更面含 `contract`/`interface` 时必须写 `CONTRACT.md`：唯一 owner、消费方表、兼容策略（三选一）、校验方式、破坏性判定 |
| `STD-CONTRACT-ASSERTED` | heavy | 机器 | 削弱 | 是 | `CONTRACT.md` 的"校验方式"必须指向可运行的断言命令 |

### 流程与留痕

| id | 档位 | 判定 | 违反后果 | 可豁免 | 要求 |
|---|---|---|---|---|---|
| `STD-COMMIT-MESSAGE` | all | 机器 | 提示 | 是 | 规则见 [`tools/validate-commit-msg.mjs`](../tools/validate-commit-msg.mjs)（本文档不重复定义） |
| `STD-EXEMPTION-DECLARED` | all | 机器 | 阻断 | **否** | 任何豁免都要含 `reason` 与 `clear_when`；豁免**只减不增** |
| `STD-SCOPE-NOT-CLAIMED` | all | 人工 | 提示 | 是 | 未接入/未体检的仓必须显式标注"无结论"，不得默认为合格 |

### 不可豁免的产品底线（汇总）

以下 6 条**不允许项目覆盖**，因为它们是本产品"结论可信"的前提：

```
STD-GATE-NEGATIVE-EVIDENCE     负向对照必须含失败证据（只看退出码会空转）
STD-EVIDENCE-BY-COMMAND        结论必须由命令支撑（只写结论等于没证据）
STD-EVIDENCE-INDEPENDENT-REVIEW 声称独立复核必须留痕（防顺序倒置）
STD-UNVERIFIED-EXPLICIT        未验证必须显式登记（未验证 ≠ 可以）
STD-CONTRACT-FROZEN            契约面必须冻结清单（否则各方靠口头对齐）
STD-EXEMPTION-DECLARED         豁免必须含清除条件（否则等于永久放弃）
```

## 三、如何制定/覆盖你自己的规则

标准的设计前提是：**产品给底线，项目给上下文**。因此覆盖机制只有一处，且优先级明确。

### 优先级

```
项目自定义（devflow.json 的 standards 段）  >  产品基础标准（spec/standards.json）
```

例外：**不可豁免项不允许覆盖** —— 你声明了也会被**拒绝并告知原因**（在 `devflow standards` 输出中显示为"项目覆盖被拒绝"）。

### 覆盖单条标准

在项目根 `devflow.json` 里加 `standards.overrides`：

```jsonc
{
  "devflow": { "project": "my-service", "kit": "^1.0.0" },
  "gates": { "...": "..." },
  "standards": {
    "overrides": [
      {
        "id": "STD-GATE-NEGATIVE-CONTROL",
        "judge": "met",
        "reason": "本项目的构建门禁是第三方 CLI，无法构造有意义的失败对照；已用集成测试覆盖该风险",
        "clear_when": "引入可控的构建失败用例后移除本条覆盖"
      }
    ]
  }
}
```

要点：

- `judge: "met"` 表示"本项目按此标准判定为满足"；
- `reason` 与 `clear_when` **必填** —— 没有清除条件的覆盖会被 `STD-EXEMPTION-DECLARED` 判为未满足；
- 覆盖会**留痕**：`devflow standards` 与 `devflow status` 会显示"项目已覆盖：<你的理由>"。

### 追加自己的标准

产品标准之外，你可以补充项目自己的约束（它们会与基础标准一起被判定）：

```jsonc
{
  "standards": {
    "additional": [
      {
        "id": "STD-LOCAL-API-VERSION",
        "title": "对外接口必须带版本前缀",
        "tier": "all",
        "judge": "manual",
        "consequence": "info",
        "exemptable": true,
        "reason": "本项目对外网关要求 /v1 前缀"
      }
    ]
  }
}
```

> `judge: "manual"` 的条目不会自动判定，只会在报告中列出提醒 —— 这是刻意的：
> 能自动化的才自动化，不能的就明确说"需人工"，而不是假装已检查。

### 登记豁免（与覆盖的区别）

| 手段 | 用途 | 位置 | 显示为 |
|---|---|---|---|
| **覆盖**（`standards.overrides`） | 这一条**不适用于**本项目（口径不同） | `devflow.json` → `standards` | 项目已覆盖（附理由） |
| **豁免**（`baseline_exempt` / `baseline_debt`） | 这一条**暂时达不到**，是已知债务 | `devflow.json` → `gates.<门禁>` | ■ 基线豁免 / ⚠ 削弱（**绝不显示为 ✓**） |

**别把债务写成覆盖。** 覆盖意味着"标准不适用"，豁免意味着"欠着" —— 后者必须带 `clear_when` 且只减不增。

## 四、常见问题

**Q：`devflow standards` 报"不适用：未取到门禁记录"？**
先跑一次 `devflow gate run <变更>`。没有门禁记录时，引擎**拒绝**判定测试相关条目（而不是乐观地判为通过）。

**Q：为什么我的门禁明明失败，标准却只报"削弱"而不是"阻断"？**
因为你**诚实登记了** `baseline_debt`。分级是刻意的：谎报才阻断。

**Q：覆盖被拒绝了怎么办？**
看输出里的原因。不可豁免项（见第二节末）只能通过**修**来满足，不能通过配置绕过。若你认为某条不该是不可豁免，请提 issue 讨论 —— 那是**产品决策**，不是项目配置能改的。

**Q：我能不能完全不用这套标准？**
可以不用这个产品；但只要用 `devflow`，不可豁免项就始终生效。这是本产品"结论可信"的代价。

## 五、哪些是"强制"，哪些只是"约定"（重要）

本产品只对**能机械判定**的事情负责。下面把 `spec/roles.json` 的 6 条角色约束如实分档 ——
**不要把它们混为一谈**：

| 约束 | 内容 | 强制方式 | 谁保证 |
|---|---|---|---|
| **R1** | 一个执行者 = 一个写入范围；任意两个的读写文件集合不得相交 | ✅ **机械强制** | 引擎（`doctor` 的 **D12**，读 `TASKS.md` 的「写入范围」列） |
| **R6** | 分组必须按文件集合是否相交计算，不得凭感觉切分 | ✅ **机械强制** | 同上（D12 用路径前缀判定相交） |
| **R2** | 契约文件只有编排者可改；执行者只使用冻结快照 | ⚠ **约定**（工具无法强制） | **执行者自觉** |
| **R3** | 同仓多模块可并行，但必须各自使用独立工作树与独立分支 | ⚠ **约定**（工具无法强制） | **执行者自觉** |
| **R4** | 验证者必须来自独立上下文；单人场景下必须新开会话 | ⚠ **约定**（工具无法强制） | **执行者自觉 + 复核留痕** |
| **R5** | 执行者无法向用户提问：所有确认点只能发生在编排者层 | ⚠ **约定**（平台能力决定） | **平台/执行者** |

### 为什么 R2–R5 无法强制

| 约束 | 结构性原因 |
|---|---|
| R2 | 引擎无法区分"编排者"与"执行者"的写入 —— 它们可能用同一个系统账户、同一个工作树。**文件系统层面没有身份**。 |
| R3 | `devflow` 运行在单仓目录内，看不到工作树的创建方式（是 `git worktree`、`clone` 还是同一份拷贝）。 |
| R4 | 引擎只能校验"有没有复核留痕"（由 `STD-EVIDENCE-INDEPENDENT-REVIEW` + 门禁 G1b 负责），**无法证明复核者真的换了上下文** —— 那是执行者的诚实问题。 |
| R5 | 取决于平台是否允许子代理向用户提问，不属于工作流引擎的能力范围。 |

### 这对使用者意味着什么

- **可以依赖工具的部分**：R1/R6（写入范围相交会被报出；若任务表缺「写入范围」列，D12 会明确说"无法判定"，而不是默默放过）；
- **必须自己守的部分**：R2–R5。**工具不会替你检查，出错时也不会拦你**；
- **建议的补偿手段**：把 R2–R5 写进团队约定与 Code Review 清单，并在 `APPROVALS.md` 里留痕（例如"复核由 X 在独立会话完成"）。

> **本产品的承诺边界**：凡是它说"✓"的，都经过了机械判定；凡是它**不能**判定的，它会说"无法判定"。
> **它不会对 R2–R5 这类约定给出任何"通过"的暗示** —— 这正是它区别于"看起来配好了"的地方。
