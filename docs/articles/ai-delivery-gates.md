# AI 写的方案怎么验收？用门禁，不用感觉

做流程工具的时候，我们遇到过一件挺讽刺的事。

演示前一切正常：门禁跑绿，状态推进到「待验证」。等到要发布，同一条门禁却显示「尚未运行」——刚跑绿的结果，在发布这一步被判成了没跑过。

查下来是我漏传了一个参数：`gate run` 直接调判定函数，没把上一次的运行记录传进去，而发布前的那道闸刚好要读它。修起来只有三行，但暴露的问题不小：连**「检查」本身**都会骗人。

所以这篇不讲怎么让 AI 写得更好，只讲怎么确认它「写完了」——而且这个确认过程本身要经得起检查。

## 能机械验证的只有四类

| 能验证 | 不能验证 |
|---|---|
| 产物在不在（文件、章节、表格列） | 方案对不对（业务判断） |
| 内容填没填（占位符、空章节） | 写得好不好（品味） |
| 证据全不全（命令、退出码、输出尾部） | 客户认不认（关系） |
| 门禁是不是恒真（负向对照） | 市场时机 |

门禁只做左边这一列。右边交给人和时间，把能机械化的先机械化，人才有空判断真正需要判断的。

## 一条门禁，至少回答四个问题

大多数团队的门禁写成这样：

```json
{ "test": { "run": "npm test" } }
```

它只回答**「退出码是不是 0」**。这不够，因为退出码为 0 有两种可能：真的通过了，或者根本没检查。

一条可信的门禁要能回答：跑的是什么（命令原文）、退出码是多少、输出尾部是什么、以及它是不是恒真（拿一个必定失败的输入，它必须失败）。最后一条最容易被跳过，也最值钱。

我们把它做成了自检用例，下面五条都是踩过的：

| 写法 | 为什么骗人 | 正确做法 |
|---|---|---|
| `"run": "exit 0"` | 永远通过 | 声明负向对照，必须返回非零 |
| 负向对照返回 1，实际是 `No test files found` | 断言从没执行 | 同时要求失败证据（`Failures: 1`、`AssertionError`） |
| `cmd \| tail -1` 取结论 | 管道退出码来自 `tail`，恒为 0 | 取被调用命令自身的退出码 |
| 计数正则只取第一行 | 多模块把 15 个测试记成 4 个 | 累加所有匹配 |
| 测试数下限设为 0 | 0 个测试也算通过 | 给真实下限 |

## 门禁不够，还要状态机

门禁回答「这一步能不能过」，不回答「现在该做什么」。

一个变更从想法到发布有必然顺序：需求、判据、契约、实现、提测、验证、发布。没有状态机，就会出现代码写完才补需求、发布前才想起验证。

状态机的价值不是流程感，是缺件即拒绝：

```
草稿 → 需求就绪 → (契约冻结) → 实现中 → 待验证 → 已验证 → 已发布
```

每一步声明「进入这一步必须有哪些产物」。少一件，`advance` 直接拒绝，并告诉你缺哪个文件、哪一节。轻档跳过「契约冻结」，微档跳过大半——跳过是声明，不是漏跑。

## 发布要单独设一道闸

最常见的失真：提测时门禁是绿的，发布时拿的还是那次记录。代码早改过了，记录还是绿的。于是发布这个词，变成了点一下。

我们的做法是让项目声明 `release.requires`，列出的门禁在进入「已发布」前必须各有一条 pass 记录，而且：

- 记录要比最近一次产物修改更新，旧记录不算证据；
- `⚠ 未验证通过`和豁免都不算通过；
- `advance --to released` 会先现跑一遍，不等你手动跑。

想用 `--no-run` 跳过也可以，但旧记录会因新鲜度被判无效。

## 怎么开始，不用重构项目

给现有项目接上：`curl -fsSL …/install.sh | sh`，然后 `devflow init`、`devflow doctor`。

doctor 的作用是回答「现在这套门禁能不能信」。它会点出恒真门禁、缺负向对照、仍是占位脚本的情况，并给修法。信它，别信自己读一遍的感觉。

接下来把测试、构建、数据体检写成项目自己的命令，配上负向对照；给发布加 `release.requires`。

AI 让产出变便宜，验收就成了瓶颈。门禁不提高产出速度，它只保证一件事：你说「完成」的时候，有东西能证明。
