# 门禁参考（G0–G8）：每条门禁防的是哪一种"看起来通过"

> **这份文档可以单独引用。** 它不是使用指南（那是 `00-quickstart.md`），而是**判据清单**：
> 每条门禁在防哪种失真、通过条件是什么、留下什么证据、真实踩过什么坑。
> 给别人做评审时，直接把「反例库」那一节贴过去即可。
>
> **机器正典**是 `spec/gates.json`（引擎真正读的那份）。本文与它不一致时，以 JSON 为准，
> 并请提 issue —— 文档与正典漂移本身就是本产品要消灭的缺陷。

---

## 一、判定语言

| 符号 | 判定 | 含义 | 允许推进？ |
|---|---|---|---|
| ✓ | `pass` | 通过，且有可复核证据 | 是 |
| ⚠ | `unverified` | **未验证通过**：跑了，但不能证明它有效（如恒真门禁、未声明负向对照） | 视档位，通常需人工确认 |
| ■ | `exempt` | 基线豁免：存量债务，显式登记且只减不增 | 是（但绝不显示为 ✓） |
| ✗ | `fail` | 执行失败 | 否 |
| ⛔ | `blocked` | 前置条件不成立，拒绝判定 | 否 |
| ○ | `pending` | 未运行 | 否（G2 会拦） |
| ⏸ | `stale` | 确认点超时 | 否 |

**一句话规则**：`unverified` 永远不等于 `pass`。这是整套体系最容易被"优化"掉、也最不能丢的一条。

## 二、总表

| 门禁 | 名称 | 层级 | 防的失真 |
|---|---|---|---|
| G0 | 项目配置有效 | 阻断 | 配置缺失/非法/版本不满足时**静默降级**继续跑 |
| G1 | 产物齐备 | 阻断 | 该写的文档没写，流程却继续推进 |
| G1b | 内容合规 | 阻断 | 文档有骨架没内容：AC 无判据、验证没覆盖 AC、签名是占位 |
| G2 | 证据形态 | 阻断 | 结论有、证据无（"我跑过了"） |
| G3 | 负向对照 | **标签** | 门禁恒真（`exit 0`），永远通过 |
| G4 | 上下文预算 | 阻断 | 单个变更塞爆上下文，模型开始丢信息 |
| G4b | 指令链预算 | 阻断 | 指令文件过多，宿主优先丢弃较宽泛的规则 |
| G5 | 状态一致 | 阻断 | STATE、STATUS.json、产物三者互相矛盾；未知状态被当合法 |
| G6 | 基线豁免合规 | 阻断 | 用"豁免"把新债洗成旧债，或拿豁免绕过大变更 |
| G7 | 变更面与档位匹配 | **标签** | 静默降档：轻档悄悄改了接口/契约 |
| G8 | 产物运行时健全性 | 阻断 | 构建退出码 0，但产物根本跑不起来 |

## 三、逐条：判据、证据、真实反例

### G0 项目配置有效（阻断）
- **判据**：`devflow.json` 存在 → 合法 JSON → 含 `devflow` 块 → kit 版本满足约束 → 至少声明一个门禁。
- **证据**：`configPath` / `resolvedRoot` / `kitVersion` / `declaredGates`。
- **反例**：版本不满足时"降级运行"，用旧引擎读新规范 —— 读不懂的字段被忽略，门禁静默少跑几条。
  **正确做法**：直接阻断并报错，不静默降级。
- **自查**：`devflow doctor` 的 D1 分组。

### G1 产物齐备（阻断）
- **判据**：`stateChain(当前状态, 档位, 从哪个状态起飞)` 所需产物全部存在，且**必填章节 / 必填列 / 最少行数**都在。
- **证据**：`state` / `tier` / `present` / `missing` / `sectionErrors`。
- **反例**：只检查"文件在不在"。文件在、章节空，等于没写。G1 必须连结构一起查。
- **自查**：`devflow advance <item> --check` 会点名缺哪个文件、哪一节。

### G1b 内容合规（阻断）
- **判据**：每条 AC 有判据与判据类型；任务能追溯到 AC；验证记录覆盖全部 AC；确认记录达到档位要求且**不是占位**；声称"独立复核"必须有复核留痕。
- **证据**：`acceptanceCriteriaHaveJudgement` / `tasksTraceable` / `verificationCoversAllAC` / `approvalsRecorded` / `noPlaceholderContent`。
- **反例**（三个都真实发生过）：
  1. 模板里写着 `（姓名）`、`通过 / 驳回`，被当成"已填写" → `isRealValue()` 把占位与未选定选项判为假；
  2. 复核记录只写"我复核过了，没问题" → 必须有具体复核方 +（时间戳或实测证据）；
  3. 声称"独立复核"却没有任何留痕 → 直接阻断（SC32 钉住）。
- **自查**：`devflow gate run <item>` 的 G1b 行。

### G2 证据形态（阻断）
- **判据**：每条门禁结果含 **命令原文 + 退出码 + 输出尾部**，缺一即阻断。
- **证据**：`records`。
- **反例**：把 `cmd | tail -1` 的退出码当结论 —— 管道退出码来自 `tail`，永远是 0。
  引擎取的是**被调用命令自身的退出码**，不是管道的。
- **自查**：`devflow status --digest`。

### G3 负向对照（标签级，`strict` 可升级为阻断）
- **判据**：项目为该门禁声明的"必定失败"命令必须返回非零，**且输出里要有明确的失败证据**。未声明、返回 0、或只有退出码没有失败证据 ⇒ 该门禁记 ⚠。
- **证据**：`project` / `gate` / `controlCommand` / `controlExitCode` / `controlOutputTail` / `verifyExitCode`。
- **反例**：负向对照返回 1，但原因是 `No test files found, exiting with code 1` —— 断言**从未执行**，门禁却显示"负向对照返回 1，门禁可信"。
  **正确做法**：`hasFailureEvidence()` 要求出现 `Failures: 1` / `AssertionError` / `BUILD FAILURE` / `error TS####` / `[ERROR]` 等真实失败标记。
- **注意**：G3 不出现在 `gate run` 的独立行里，它贴在**每一条项目门禁行**上（`✓ test exit=0 count=12  负向对照返回 1，门禁可信`）。`gate run` 显示 9 行而不是 10 行，不代表 G3 没跑。

### G4 / G4b 上下文预算（阻断）
- **判据**：单个变更产物总量：警告线 120k、阻断线 250k；指令链上限 64k。不依赖分词器（零依赖），按字符量级估算。
- **证据**：`itemKb` / `largestFiles` / `instructionChainKb`。
- **反例**：把整份设计文档塞进一个变更 —— 门禁能过，但模型读到一半开始丢约束，产物质量下降且**无法归因**。

### G5 状态一致（阻断）
- **判据**：`STATE` 与 `STATUS.json` 一致；门禁记录匹配状态要求；**出现未定义状态直接报错**。
- **证据**：`stateFile` / `statusState` / `lastRun`。
- **反例**：状态写错字（`deploying`）被当作合法状态继续跑，整条状态机的校验全部失效。
  引擎把这种情况记为 `fatal`，不只是阻断。

### G6 基线豁免合规（阻断）
- **判据**：豁免必须显式登记原因与清除条件；触碰契约/接口的变更不得引用豁免；新建项目禁止豁免。
- **证据**：`exemptions` / `clearConditions`。
- **反例**：把"存量项目没有测试"写成永久豁免 —— 从此测试数可以为 0 而不被拦。
  **正确做法**：显示为 ■（豁免）而不是 ✓（通过），并且**只减不增**。

### G7 变更面与档位匹配（标签级，启发式）
- **判据**：对比档位与实际变更面（contract / interface / data / auth）。轻/微档却触碰接口面 ⇒ ⚠ 需人工确认。
- **证据**：`tier` / `changeSurface` / `inspectedPaths` / `signals`。
- **反例**：12 行"小改动"顺手改了返回结构，没走契约冻结，下游静默崩。
- **边界（必须明说）**：这是**启发式**，会漏报。它换来的价值是"不静默放过"，不是"绝不放过"。

### G8 产物运行时健全性（阻断）
- **判据**：小程序产物（`dist/` `build/` `out/` 下的 JS）不得残留 `process.env`。
- **证据**：`files`（命中文件，最多 3 个）/ `scanned`。
- **反例（真实演练）**：`.env` 里少了 `TARO_APP_*` 变量，Taro 不替换该成员表达式 ⇒ 产物残留 `process.env.X` ⇒ 小程序没有 `process` 全局对象 ⇒ `app.js` 直接 `ReferenceError`，所有页面"has not been registered yet"，整包不可用。
  **而构建退出码是 0。** 这就是"门禁谎报通过"的典型：只看退出码，不看产物能不能跑。

## 四、反例库：12 种"能过但不算数"的写法

| # | 错误写法 | 为什么骗人 | 正确做法 |
|---|---|---|---|
| 1 | `"test": { "run": "exit 0" }` | 门禁恒真，永远 ✓ | 声明负向对照：`negative_control` 必须非零 |
| 2 | 负向对照只判退出码 | 退出码 1 可能来自"没找到测试文件" | 同时要求失败证据标记（G3） |
| 3 | `cmd \| tail -1` 取结论 | 管道退出码来自 `tail`，恒为 0 | 取被调用命令自身退出码 |
| 4 | 计数正则只取第一行 | 多模块把 15 个测试记成 4 个 | `matchCount` 累加所有匹配 |
| 5 | 测试数下限设为 0 | 0 个测试也算"通过" | `require_min_tests` 给真实下限 |
| 6 | 占位符当真实值 | `（姓名）` 被判"已填写" | `isRealValue()` 统一口径 |
| 7 | 只写"我复核过了" | 无复核方、无时间戳、无实测 | 复核方 +（时间戳或实测证据） |
| 8 | 未验证项列表硬编码 `[]` | 发布材料永远"0 项未验证" | 解析真实表格（`parseUnverifiedItems`） |
| 9 | 豁免写成永久 | 债务不再减少 | 登记清除条件，只减不增 |
| 10 | 状态写错字仍继续 | 状态机校验全部失效 | 未知状态直接 `fatal` |
| 11 | 只管构建退出码 | 产物残留 `process.env`，整包崩 | G8 扫产物 |
| 12 | 提交信息写成变更日志 | 定位成本上升，diff 与描述脱节 | `type(scope): 摘要` ≤72 字，正文 ≤3 条 |

## 五、三个设计选择（为什么不是"评分制"）

1. **用退出码，不用评分。** 评分可以让"同一个 AI 又改又评"，退出码不能。判据必须能被机器重复执行。
2. **G3 默认是标签而不是阻断。** 现实中很多团队一开始没有负向对照。直接阻断会让人绕过整套流程；
   记 ⚠ 能让"不可信"持续可见——**可见的弱，好过不可见的强**。
3. **G7 明示会漏报。** 启发式一旦自称完备，就会变成新的"假通过"来源。把边界写进文档，比提高准确率更重要。

## 六、怎么被别的项目引用

- **读机器正典**：`spec/gates.json`（判定、层级、检查项、证据字段、版本）。
- **只想要判据**：把本文第四节整段贴进你的 `CONTRIBUTING.md` 或 agent 指令文件。
- **想要可执行版本**：`devflow init` 后 `devflow doctor`，把 D1–D4 当作"门禁自检"。
- **改判据**：改 `spec/gates.json` 并同步本文；`test/` 下有对应单测，`scripts/selfcheck.mjs` 有对应端到端用例（SC1–SC70）。
